# Решения — Underline

Реестр ведётся только добавлением. Чтобы изменить решение, нужно создать новое и
связать его с прежним.

Словарь статусов: `Accepted` — принято и действует; `Proposed` — предложено с
обоснованием и источниками, но не принято, реализовывать нельзя; `Deferred` —
предложение сознательно отложено за границу текущего среза решением, которое его
откладывает; `Superseded→DEC-####` — заменено более поздним решением. Статус
предложенного решения меняет только тот, кто принимает.

### DEC-0006 — Журнал пространства выступает Delivery Service

- **Date:** 2026-09-14
- **Status:** Superseded→DEC-0020 (правило порядка для v1); лидерлесс-вариант — OQ-0008
- **Context:** RFC 9420 §14 требует, чтобы приложение установило способ разрешения конфликтующих Commit для одной эпохи. Прежний инвариант архитектуры ссылался на «правила MLS», которых не существует; без секвенсора два одновременных commit'а дают две эпохи, и половины группы перестают расшифровывать друг друга.
- **Decision:** Commit является событием журнала. Побеждает первый валидный Commit эпохи по порядку журнала; при ничьей — меньший хеш `FramedContent`. Commit принимается только при `epoch == current + 1`. Welcome удерживается, пока commit не подтверждён победителем. Окно удержания прошлых эпох — `MaxEpochs(2)` с ограничением по времени, равным TTL почтового ящика. Каждое прикладное событие несёт `(epoch, epoch_authenticator[..8])`; несовпадение при равной эпохе — сигнал форка без ложных срабатываний. Восстановление — `recover_fork_by_readding`, в крайнем случае `reboot`.
- **Consequences / affects:** `docs/ARCHITECTURE.md`, `docs/research/2026-09-14-mls-measurements.md`, репозиторий `underline-cli`
- **Source:** исследование 2026-09-14 · `docs/research/2026-09-14-mls-measurements.md` · RFC 9420 §14, RFC 9750 §5.2

### DEC-0007 — Предлагать может каждый, коммитить — детерминированно выбранный

- **Date:** 2026-09-14
- **Status:** Superseded→DEC-0020
- **Context:** RFC 9420 §14 предупреждает: в достаточно активной группе участник может никогда не суметь отправить Commit, потому что всегда проигрывает. Конкуренция commit'ов — не редкое событие, а постоянный режим, если коммитить может каждый.
- **Decision:** Любой участник вносит предложения (Add, Remove, Update, SelfRemove). Коммиттер на эпоху выбирается детерминированно ротацией `leaf_index mod epoch`, одинаково у всех клиентов. Предложения батчатся. Конкуренция становится редким исключением, а разрешение по DEC-0006 — страховкой, а не основным путём.
- **Consequences / affects:** `docs/ARCHITECTURE.md`, репозиторий `underline-cli`
- **Source:** исследование безопасности 2026-09-14 · `docs/security/threat-model.md`

### DEC-0008 — Почтовый ящик с TTL обязателен, а не опционален

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025)
- **Context:** OQ-0002 ставил ящик как компромисс приватности ради доставки. Исследование показало другое: без store-and-forward офлайновые участники пропускают Commit, а пропущенный Commit — главный генератор форков. Ящик нужен для корректности протокола, а не для удобства.
- **Decision:** Единица хранения — пространство, а не устройство. Тег слота `T_i = HMAC(MLS-Exporter("underline mailbox", epoch), i)`, где `i` — суточный слот; ключи записи и чтения для пары (пространство, слот) выводятся из того же exporter-секрета. Ящик хранит `[тег | добитый до корзины ciphertext | срок]` и ничего больше: ни IP в таблице, ни журналов соединений. TTL 7–30 суток, равный окну удержания эпох из DEC-0006. Ящик поставляется одним статическим бинарём, который может поднять друг.
- **Consequences / affects:** `docs/OPEN_QUESTIONS.md` OQ-0002, `docs/security/metadata.md`, `docs/ARCHITECTURE.md`
- **Source:** исследование 2026-09-14 · `docs/security/metadata.md`

### DEC-0009 — Транспорт — iroh, но всегда с собственным пресетом

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025)
- **Context:** OQ-0001 выбирал между iroh и libp2p. Измерено 2026-09-14: размеры бинарей практически равны (3,39 МБ против 3,24 МБ), но у iroh адрес и есть ключ, а у libp2p нужно самому собирать транспорт, безопасность, мультиплексор, relay, DCUtR и AutoNAT и держать свои bootstrap-узлы. Пробивание NAT: у libp2p измерено 70 % ± 7,1 % на 4,4 млн попыток, у iroh заявлено ~9 из 10 без независимой проверки.
- **Decision:** Транспортом становится iroh. Пресет по умолчанию не используется никогда: своё реле, глобальное обнаружение выключено, публикация в pkarr и `dns.iroh.link` выключена, mDNS только при явном включении для доверенной сети. Обоснование запрета: пресет по умолчанию отдаёт одной третьей стороне весь граф соединений, поскольку пробивание NAT координируется через домашнее реле, и глобальный оракул присутствия через публикуемые записи.
- **Consequences / affects:** `docs/OPEN_QUESTIONS.md` OQ-0001, `docs/security/metadata.md`, репозиторий `underline-cli`
- **Source:** исследование 2026-09-14 · `docs/security/metadata.md`

### DEC-0010 — Каталогом адресов и членства служит журнал, а не DHT

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025)
- **Context:** У проекта нет задачи поиска контактов: друзья добавляются вне полосы. Есть задача «где этот известный пир сейчас». DHT решает её ценой публичного оракула присутствия: идентификатор Tox позволял узнать IP цели (CVE-2018-25022), а запросы Kademlia раскрывают искомый ключ каждому узлу на пути.
- **Decision:** Устройство публикует подписанное событие `{endpoint_id, relay_url, direct_addrs, valid_until}` с коротким сроком в журнал каждого пространства, где состоит. DHT не используется. При синхронизации стороны обмениваются не идентификаторами пространств, а тегами `HMAC(MLS-Exporter("underline space tag", epoch), nonce_пары)`: посчитать тег может только действующий участник, у исключённого совпадения прекращаются с эпохи удаления.
- **Consequences / affects:** `docs/ARCHITECTURE.md` раздел о репликации, `docs/ux/scenarios.md` SCN-005, `docs/security/metadata.md`
- **Source:** исследование безопасности 2026-09-14 · `docs/security/threat-model.md`

### DEC-0011 — Ключи программные, обёрнутые железом; журнал шифруется вместе с ними

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025); формат seed и шифронабор приняты в DEC-0021
- **Context:** OQ-0006 спрашивал про формат и хранение ключей. Измерено: Secure Enclave умеет только P-256, в Windows CNG нет Curve25519, Android StrongBox её не держит. MLS работает на X25519 и Ed25519. Переход на шифронабор 0x0002 не спасает: провайдер `openmls_libcrux_crypto` его не реализует, а Secure Enclave не умеет HPKE в форме RFC 9180.
- **Decision:** Шифронабор MLS остаётся на X25519 и Ed25519; 0x0002 объявляется поддерживаемым в `Capabilities`, но не используется. Железо оборачивает один 32-байтный ключ хранилища устройства (Secure Enclave ECIES, DPAPI, Android Keystore, Secret Service на Linux с честным файловым откатом). Этот ключ шифрует одну базу SQLCipher, где лежат и состояние MLS, и журнал событий — шифровать ключи, оставив журнал открытым, бессмысленно. `secure_delete=ON`, каталог исключён из облачных бэкапов. Каждая операция MLS выполняется в транзакции, при ошибке группа перечитывается с диска: аудит SRLabs оставил находку S1-3 о неатомарных изменениях состояния непочиненной.
- **Consequences / affects:** `docs/OPEN_QUESTIONS.md` OQ-0006, `docs/research/2026-09-14-key-custody.md`, оба клиентских репозитория
- **Source:** исследование 2026-09-14 · `docs/research/2026-09-14-key-custody.md`

### DEC-0012 — Личность подписывает журнал устройств; leaf вне списка не принимается

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025); байты учётки приняты в DEC-0021
- **Context:** Добавление постороннего устройства под чужой личностью — это предложение GCHQ о «ghost user», и оно не теоретическое. Ручную сверку отпечатков без подсказки находят 14 % пользователей, поэтому защита не может опираться на действие человека.
- **Decision:** Корневой ключ личности (Ed25519) подписывает журнал устройств, ведущийся только добавлением, включая отзывы. MLS-leaf несёт учётку с ключом устройства и хешем последней версии журнала; клиент собеседника отвергает Add, если leaf'а нет в подписанном списке. Изменения состава — сообщения ленты, а не сворачиваемые уведомления. Запрос истории новым устройством требует подписи принимающей личности, ограничен по глубине политикой пространства и сам является видимым событием. Восстановление личности: эскроу seed в iCloud Keychain и Android Block Store плюс 2-из-3 Шамира между контактами; история приходит от участников пространства.
- **Consequences / affects:** `docs/OPEN_QUESTIONS.md` OQ-0004, `docs/research/2026-09-14-key-custody.md`, оба клиентских репозитория
- **Source:** исследование 2026-09-14 · `docs/research/2026-09-14-key-custody.md`

### DEC-0013 — Приглашение и привязка устройства — разные типы с разными парсерами

- **Date:** 2026-09-14
- **Status:** Superseded→DEC-0024 (форма SCN-002); грамматика ссылок — Deferred (DEC-0025)
- **Context:** Атака с наибольшим произведением вероятности на ущерб — не криптографическая. Аккаунты Signal в 2025 году компрометировали, подсовывая QR «приглашение в группу», который был запросом на привязку устройства. У Underline те же два артефакта.
- **Decision:** Форматы `underline://join/…` и `underline://enrol-device/…` различны, декодируются разными путями кода и подтверждаются разными экранами. Приглашение физически не способно добавить leaf под личностью получателя. Привязка устройства требует кода, показанного уже существующим устройством. Приглашение самозаверено подписью над всем блобом и несёт отпечаток создателя, имеет короткий срок жизни и предпочитает QR или локальную передачу копированию через буфер обмена. GroupInfo не попадает ни в один пересылаемый артефакт, а внешние вступления в первой версии не используются: держатель GroupInfo вступает без согласия участников (RFC 9420 §12.4.3.2).
- **Consequences / affects:** `docs/ux/scenarios.md` SCN-002 и SCN-003, оба клиентских репозитория
- **Source:** исследование безопасности 2026-09-14 · `docs/security/threat-model.md`

### DEC-0014 — Подпись события привязана к домену, идентификатор выводится из содержимого

- **Date:** 2026-09-14
- **Status:** Superseded→DEC-0019
- **Context:** Каноничность кодирования обеспечивает воспроизводимость, но не отделяет контексты: подпись из одного пространства принимается в другом. Идентификатор, выбираемый автором, позволяет участнику заранее занять id и вытеснить чужое событие через дедупликацию.
- **Decision:** Подписывается `(домен ‖ space_id ‖ epoch ‖ тип ‖ родители ‖ нагрузка)`; `event_id = H(домен ‖ то же ‖ leaf автора ‖ подпись)`; `space_id = H(события создания)`. Событие без валидной подписи не достигает реплики: тип проверенного события имеет приватный конструктор. Отвергается событие, родитель которого заявлен в более поздней эпохе. Два события одного автора с общим предком сохраняются как доказательство раздвоения и показываются — это свойство, которого нет ни у WhatsApp, ни у Signal, ни у Threema, ни у iMessage.
- **Consequences / affects:** `docs/ARCHITECTURE.md` раздел Event, репозиторий `underline-cli`
- **Source:** исследование безопасности 2026-09-14 · `docs/security/threat-model.md`

### DEC-0015 — Отказ постороннему неотличим по содержанию, размеру и времени

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025); формулировка сужена там же
- **Context:** Отказ сам по себе является информацией. Разный текст ошибки, разное время ответа и разный порядок сообщений превращают SCN-005 в оракул членства — ровно так утекала информация о существовании учётных записей в OpenSSH.
- **Decision:** Стороне, не доказавшей знание уже известного нам ключа, ответ не отправляется вовсе — принцип WireGuard. Там, где ответ необходим для прохождения NAT, он постоянного размера и с фиксированной минимальной задержкой. Все причины отказа дают один непрозрачный исход; причина пишется только в локальный журнал в редактированном виде. Состояние не заводится до доказательства знания ключа; действует лимит на источник. Эндпойнта, отвечающего «кто твои пиры», не существует даже для участника.
- **Consequences / affects:** `docs/ux/scenarios.md` SCN-005, репозиторий `underline-cli`
- **Source:** исследование безопасности 2026-09-14 · `docs/security/threat-model.md`

### DEC-0016 — Потолок пространства — 256 leaf'ов; публичные ленты не используют MLS

- **Date:** 2026-09-14
- **Status:** Proposed
- **Context:** Измерено 2026-09-14: ветка на 500 leaf'ов обрабатывает commit за 2,5 мс, то есть вычислительно тривиальна. Ломается другое: каждое устройство обрабатывает каждый commit, а разреженное дерево из пассивных участников вырождает стоимость обновления из O(log n) в O(n) — 41,6 КБ против 1,3 КБ.
- **Decision:** Пространство с MLS ограничено 256 leaf'ами. Содержимое, читаемое посторонними, не использует групповую криптографию: публичная лента — подписанный открытый текст с авторством и целостностью, отдельный примитив. Большое приватное пространство не входит в первую версию, а не обслуживается ослабленной схемой.
- **Consequences / affects:** `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/research/2026-09-14-mls-measurements.md`
- **Source:** исследование 2026-09-14 · `docs/research/2026-09-14-mls-measurements.md`

### DEC-0017 — Воспроизводимые сборки, публичный журнал релизов и пороговая подпись

- **Date:** 2026-09-14
- **Status:** Deferred (DEC-0025); гигиена сборки принята там же
- **Context:** Архитектура, не хранящая ни ключей, ни каталога, ни логов, убирает шесть правовых рычагов из восьми: хранимые данные, владение ключами, единственный ключ уровня Lavabit, ключи у организатора, сопоставление первоисточника, повальное хранение метаданных. Остаётся один — подпись бинаря. Значит он и становится целью.
- **Decision:** Сборки CLI и нативной части Chat выполняются закреплённым тулчейном в контейнере, их хеши публикуются в журнал прозрачности (Sigstore Rekor) при каждом релизе, и клиент отказывается устанавливать артефакт, подписи которого нет в журнале. Ключ подписи пороговый, 2-из-3, у разных людей. `Cargo.lock` и `package-lock.json` закреплены, сборка идёт с `--locked` и без сетевого доступа для `build.rs`, `cargo deny` запрещает неизвестные реестры, изменения в крейтах криптографии и транспорта требуют двух рецензентов. Ограничение называется прямо: сборку для iOS Apple пересобирает и переподписывает, поэтому воспроизводимость там недостижима.
- **Consequences / affects:** оба клиентских репозитория, `docs/security/threat-model.md`
- **Source:** исследование безопасности 2026-09-14 · `docs/security/threat-model.md`

### DEC-0018 — Границы первого среза: одно устройство, три десктопа, ноль серверов

- **Date:** 2026-09-14
- **Status:** Accepted
- **Context:** Двенадцать предложений DEC-0006…0017 описывали полный мессенджер — мобильные платформы, push, поручителей, публичные ленты, вложения, реле и ящик, — тогда как `docs/PRODUCT.md` и сценарии SCN-001…005 описывают первый вертикальный срез из четырёх свойств. ### DEC-0019 — Конверт события: версия, домен с поколением группы, автор по ключу, бутстрап идентификатора

- **Date:** 2026-09-14
- **Status:** Accepted
- **Context:** DEC-0014 оставил пять дыр: не было поля версии протокола и правила для незнакомых типов; домен подписи не включал поколение группы, поэтому после `reboot` эпохи начинаются заново и старое событие эпохи 1 неотличимо от нового; автор задавался индексом leaf'а, а индексы переиспользуются после удалений (RFC 9420 §7.7); `space_id = H(события создания)` при подписи события создания над `space_id` — круг; и всё это замерзает в первом же записанном журнале.
- **Decision:** Каждое событие несёт `protocol_version: u16` и `event_type: u16`. Незнакомый тип **хранится и пересылается как непрозрачный** — клиент v1 не отвергает событие v2. Подписывается кортеж `(домен ‖ protocol_version ‖ space_id ‖ group_generation ‖ epoch ‖ event_type ‖ parents ‖ payload)`, где `group_generation` растёт при каждом `reboot`/`recover`, и сравнение эпох ведётся внутри поколения. Автор — публичный ключ подписи устройства из учётки, никогда индекс leaf'а. `event_id = H(домен ‖ подписанный кортеж ‖ ключ автора ‖ подпись)`. Бутстрап: событие создания подписывается с `space_id = 0` (32 нулевых байта), и только оно; `space_id` пространства = `H(события создания)`; любое другое событие с нулевым `space_id` невалидно. Тип проверенного события имеет приватный конструктор. Кодирование — детерминированный CBOR (RFC 8949 §4.2), крейт закрепляется в `underline-core`.
- **Consequences / affects:** `docs/ARCHITECTURE.md` раздел Event, репозиторий `underline-node` (крейт `underline-core`), заменяет DEC-0014
- **Source:** аудит предложения 2026-09-14 (собственный проход + слепой рецензент) и ответы владельца в тот же день

### DEC-0020 — Единственный коммиттер и роли: создатель пространства — admin, остальные предлагают

- **Date:** 2026-09-14
- **Status:** Accepted
- **Context:** У журнала как причинного DAG нет полного порядка, поэтому «первый валидный commit по порядку журнала» из DEC-0006 не определён, единственным реальным правилом оставался min-hash, который гриндится перегенерацией `UpdatePath`; ротация `leaf_index mod epoch` из DEC-0007 выбирала число, а не leaf, попадала на пустые leaf'ы и останавливала группу при офлайне коммиттера; «удерживать Welcome до подтверждения» не имело определения подтверждения; роли, на которые ссылались пять контролей, не были определены нигде.
- **Decision:** В первом срезе Commit валиден **только** от leaf'а с ролью `admin`; Commit от любого другого leaf'а невалиден — это правило валидности истории, а не поведение клиента. Создатель пространства получает роль `admin` при создании; в личном чате admin — тот, кто его открыл. Admin передаёт роль подписанным событием `role_transfer`; в срезе admin ровно один. Остальные участники шлют предложения (Add, Remove, Update); admin батчит их в один Commit. Форки невозможны по построению, удерживать Welcome не нужно. Поле детектора `(epoch, epoch_authenticator[..8])` в событиях сохраняется как инвариант для будущей версии. Исходящее событие, не подтверждённое до обработки следующего Commit, автор перешифровывает на новой эпохе. Правило порядка для нескольких коммиттеров — OQ-0008, вводится только за версионным гейтом DEC-0019.
- **Consequences / affects:** `docs/ARCHITECTURE.md` инварианты и раздел о репликации, `docs/ux/scenarios.md`, репозиторий `underline-node`; заменяет DEC-0006 и DEC-0007 для первого среза
- **Source:** аудит предложения 2026-09-14 (собственный проход + слепой рецензент) и ответы владельца в тот же день

### DEC-0021 — Личность и учётка устройства в первом срезе; потеря устройства — потеря личности

- **Date:** 2026-09-14
- **Status:** Accepted
- **Context:** Байты учётки в leaf'е фиксируются при создании первой группы: если это голый ключ устройства, добавить второе устройство позже можно только пересозданием всех пространств. Место корневого ключа не было решено, и оба ответа что-то ломали. Совет объявить шифронабор 0x0002 поддерживаемым без реализации противоречит RFC 9420 §7.2 и гарантирует провал вступления в группу на этом наборе.
- **Decision:** Учётка leaf'а = `(identity_pk ‖ device_pk ‖ подпись identity над device_pk)`, обе пары Ed25519; seed личности — 32 байта, из которых выводится ключ, чтобы эскроу можно было добавить позже без пересоздания личности. Корневой ключ в срезе лежит на единственном устройстве, в программном хранилище с правами `0600` внутри каталога состояния — аппаратная обёртка отложена (DEC-0025), и оба клиента честно называют защиту программной. Шифронабор — `MLS_128_DHKEMX25519_CHACHA20POLY1305_SHA256_Ed25519`; `Capabilities` объявляет **только** реализованные наборы. Потеря единственного устройства — потеря личности: друзья приглашают новую, история возвращается только от участников пространств; формулировка стоит в настройках одной фразой (выбор владельца). Журнал устройств, эскроу и поручители — DEC-0025.
- **Consequences / affects:** `docs/OPEN_QUESTIONS.md` OQ-0006 → Resolved, `docs/PRODUCT.md`, `docs/ARCHITECTURE.md` разделы Identity и Device, оба клиентских репозитория; принимает часть DEC-0011 и DEC-0012
- **Source:** аудит предложения 2026-09-14 (собственный проход + слепой рецензент) и ответы владельца в тот же день

### DEC-0023 — «Удалить» означает отозвать; срок хранения по умолчанию — без ограничения

- **Date:** 2026-09-14
- **Status:** Accepted
- **Context:** Архитектура говорит, что удаление создаёт новое событие вместо перезаписи, а SSD не стирает перезаписанные страницы. Кнопка «Удалить» при этом обещала бы то, чего протокол не делает — тот же инвариант честности, что в CLI.
- **Decision:** Удаление для всех — событие `retract`, которое совместимый клиент исполняет, скрывая содержимое и показывая пометку «отозвано»; интерфейс никогда не утверждает, что сообщение удалено с чужих устройств. Удаление у себя — реальное удаление из своей реплики, с оговоркой из `docs/research/2026-09-14-key-custody.md`: невосстановимость гарантируется уничтожением ключа устройства, а не стиранием страниц. Срок хранения локальной истории на десктопе в срезе не ограничен; политика ретеншена пространства — поле события `space_policy`, значение по умолчанию «без ограничения»; ящика в срезе нет, поэтому TTL не определяется.

### DEC-0025 — Что отложено за границу первого среза и на каком условии возвращается

- **Date:** 2026-09-14
- **Status:** Accepted
- **Context:** Отложить молча — значит потерять причину и условие возврата. Каждое отложенное предложение остаётся в реестре со статусом `Deferred` и ссылкой сюда.
- **Decision:** Откладываются: почтовый ящик (DEC-0008) — возвращается вместе с WAN-транспортом, при этом теги считаются на exporter-секрете **предыдущей** эпохи и для всех удержанных эпох, чтобы отставший участник не выглядел посторонним; iroh и собственный пресет (DEC-0009) — вместе с WAN, адресные записи **вне** журнала (OQ-0009); теги пространств и адресные события (DEC-0010) — с тем же условием и с определением источника `nonce_пары` из транспортной сессии; аппаратная обёртка ключа и SQLCipher (DEC-0011) — с первым подписанным бандлом, после проверки, что `openmls_sqlite_storage` допускает общую транзакцию с таблицей событий (BL-0016); журнал устройств, эскроу и поручители (DEC-0012) — со вторым устройством; грамматика ссылок и QR (DEC-0013) — с первым внешним пользователем; DEC-0015 сужается до «ни ответа прикладного уровня, ни состояния до доказательства знания ключа» — утечку факта жизни транспорта QUIC мы принимаем; DEC-0016 остаётся предложенным без изменений; DEC-0017 — из него принимается **только** гигиена: `Cargo.lock` и `package-lock.json` закреплены, сборка с `--locked`, `cargo deny`, Dependabot; воспроизводимые контейнеры, Rekor и пороговая подпись — когда в команде будет трое, кто может держать три ключа.
