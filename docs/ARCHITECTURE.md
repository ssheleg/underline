# Архитектура Underline

Статус: направление для прототипа, 2026-08-30.

## Архитектурный тезис

Underline разделяется на четыре независимых слоя:

```text
CLI / Chat / Forum / Blog
          │
          ▼
события, пространства и репликация
          │
          ▼
OpenMLS: членство, эпохи и ключи групп
          │
          ▼
transport: direct / relay / LAN / offline bundle
```

OpenMLS не является mesh-сетью и не доставляет сообщения. По DEC-0002 он
реализует криптографический слой MLS. По DEC-0004 прикладной протокол не зависит
от конкретного транспорта.

## Доменные сущности

### Identity

Долгоживущая идентичность человека. Она подписывает разрешение на подключение и
отзыв устройств, но не обязана участвовать в каждой отправке сообщения.

### Device / Node

Отдельное устройство с собственными ключами, локальным хранилищем и сетевыми
адресами. В MLS каждое устройство представлено отдельным клиентом/leaf, чтобы
скомпрометированное или потерянное устройство можно было отозвать отдельно.

### Space

Область репликации и доступа: личный чат, группа, тема форума или лента. У каждого
пространства есть идентификатор, список авторизованных участников, MLS-группа и
локальный журнал событий.

### Event

Подписанная неизменяемая операция: сообщение, редакция, удаление, реакция или
изменение структуры. Редактирование и удаление создают новые события вместо
перезаписи истории. Для прототипа нужен канонический бинарный формат, например
deterministic CBOR, чтобы подпись и идентификатор события воспроизводились.

### Replica

Локальное материализованное состояние пространства плюс его журнал. Реплика
принимает событие только после проверки подписи, членства, схемы и причинных
зависимостей.

## Ключи и шифрование

1. При первом запуске нода создаёт локальную пару ключей идентичности устройства.
2. Для входа в пространство устройство публикует MLS KeyPackage.
3. Участник с правом приглашения добавляет устройство и передаёт ему MLS Welcome.
4. Каждое прикладное событие шифруется как MLS application message текущей эпохи.
5. Добавление или удаление участника создаёт commit и новую эпоху ключей.
6. Компрометация текущего состояния не должна раскрывать прежние эпохи, а
   удалённый участник не должен получать ключи будущих эпох — это свойства MLS,
   но корректность зависит от безопасного хранения состояния и обработки commit.

Шифрование применяется на трёх границах:

- **payload:** OpenMLS защищает сообщения пространства end-to-end;
- **transport:** QUIC/TLS или Noise защищает соединение и аутентифицирует peer;
- **at rest:** локальная база и секреты устройства защищаются средствами ОС или
  отдельным ключом хранилища.

Вложения не кладутся целиком в MLS-сообщение. Клиент генерирует ключ объекта,
шифрует и разбивает файл на чанки, а небольшой манифест с хешами и ключом передаёт
внутри MLS-события.

## Репликация

Синхронизация выполняется отдельно для каждого общего пространства:

1. ноды устанавливают аутентифицированный транспортный канал;
2. обмениваются списком идентификаторов пространств, не раскрывая посторонние;
3. для пересечения сравнивают компактное состояние журнала;
4. запрашивают недостающие зашифрованные события и объекты;
5. проверяют подписи, членство, MLS-эпоху и зависимости;
6. применяют события идемпотентно к локальной реплике.

Правило доступа: контакт с участником не переносит членство автоматически. Нода
может ретранслировать ciphertext пространства только тому peer, который способен
предъявить актуальное членство или иное протокольное разрешение.

Для прототипа события образуют append-only журнал с уникальными идентификаторами и
причинными ссылками. CRDT нужен только для тех объектов, где действительно есть
конкурентное редактирование; порядок чата не требует превращать всю систему в
один глобальный CRDT.

## Несколько устройств и история

Новое устройство пользователя добавляется в каждое пространство как новый MLS
клиент. Welcome даёт ему текущее состояние группы, но не расшифровывает старую
историю автоматически. История передаётся отдельно с уже доверенного устройства
после явного подтверждения и шифруется для нового устройства. Точная политика
глубины истории и восстановления открыта в OQ-0004.

## Доставка и обнаружение

Транспорт реализует обнаружение peers, NAT traversal, прямые соединения и relay.
Кандидаты для первого сетевого прототипа зафиксированы в OQ-0001. Relay не должен
получать MLS-ключи и может хранить только ciphertext, если такая возможность будет
принята.

Строгий режим без промежуточного хранения гарантирует приватность архитектурой,
но не гарантирует доставку, если устройства участников никогда не бывают онлайн
одновременно. Этот компромисс нельзя скрывать за словом «mesh».

## Критические инварианты

- plaintext не покидает устройство вне E2EE-контекста;
- устройство не получает данные пространства без проверяемого членства;
- повторная доставка события безопасна и не создаёт дубль;
- событие имеет стабильный идентификатор и проверяемого автора;
- удаление устройства прекращает доступ к будущим эпохам;
- конфликтующие MLS commits не применяются молча: группа выполняет rebase/retry по
  правилам MLS;
- транспорт не определяет формат прикладных событий и не владеет ключами групп;
- потеря всех авторизованных реплик означает потерю данных, если не принят
  зашифрованный backup/mailbox.

## Граница CLI-прототипа

По DEC-0003 CLI должен поддержать:

- инициализацию локальной ноды;
- создание пространства;
- экспорт приглашения и импорт Welcome;
- отправку и чтение MLS application messages;
- синхронизацию двух локально запущенных процессов;
- просмотр peers, пространств, эпох и состояния синхронизации без вывода секретов.

Первая версия может использовать loopback-транспорт, сохраняя интерфейс транспорта
сменным. Красивый интерактивный TUI на Ratatui имеет смысл после доказательства
сквозного сценария; командный каркас строится на Clap.
